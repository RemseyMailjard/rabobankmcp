Build your first MCP server.
Then learn who holds the controller.

The hard part of MCP isn't the syntax — it's knowing which of the three primitives a capability should be. The answer is always the same question: who decides when it runs?

You'll build one server around a synthetic mortgage-advice domain, adding tools, resources and a prompt one piece at a time. By the end you'll have a working server and a mental model you can apply to anything.

00

Setup & scaffold

MCP exists to solve the N×M problem: instead of writing a custom integration for every model-and-tool pair, you write one server that any MCP client can talk to. A server exposes capabilities; a client discovers them at runtime through paired list / call methods.

FastMCP removes the protocol boilerplate so you can focus on the capabilities themselves. We'll manage Python with uv — it's fast, and it can run a single file without any project setup.

terminal · install uv (once)
# macOS / Linux
curl -LsSf https://astral.sh/uv/install.sh | sh
# Windows (PowerShell)
# powershell -ExecutionPolicy ByPass -c "irm https://astral.sh/uv/install.ps1 | iex"

Create server.py. The first four lines are PEP 723 inline metadata: the file declares its own dependencies, so uv run installs FastMCP on the fly — no virtualenv, no install step. For now the server does nothing but start; that's deliberate. Run it once so you know the plumbing works before adding any capability.

server.py
# /// script
# requires-python = ">=3.10"
# dependencies = ["fastmcp"]
# ///
from fastmcp import FastMCP

# The name is what clients show in their UI.
mcp = FastMCP("rabo-mortgage-advisor")

# Synthetic sample data. In a real server this would come from
# an internal rate service. We expose it as a RESOURCE later.
MORTGAGE_RATES = {
    "annuity-10y-fixed": 3.65,
    "annuity-20y-fixed": 4.10,
    "annuity-30y-fixed": 4.35,
    "linear-20y-fixed": 4.05,
    "variable": 4.80,
}
MAX_DTI_RATIO = 0.30  # max share of gross income for housing

if __name__ == "__main__":
    mcp.run()  # stdio transport — ideal for a first, local server
terminal · run it
uv run server.py   # uv resolves FastMCP from the inline metadata, then starts the server

The fastest way to see what your server exposes is the MCP Inspector. It connects to your server and lets you call every primitive by hand, so you watch the raw protocol instead of guessing.

terminal
uv run fastmcp dev server.py   # opens the Inspector in your browser
✓
Checkpoint

The Inspector connects and shows your server name. Tools, Resources and Prompts tabs are all empty — you're about to fill them, one per step.

▸Why connect a client before writing any capability?

Capability negotiation happens once, at initialize. The client asks what the server supports and the server answers. Starting from an empty-but-running server means every capability you add appears the moment you reload — you always know whether a problem is in your code or in the connection.

▸Prefer a real project over a single file?

The inline metadata keeps this lab to one self-contained file. When it grows into something you maintain, switch to a uv project so the dependencies live in pyproject.toml and a lockfile:

terminal
uv init rabo-mcp-lab
cd rabo-mcp-lab
uv add fastmcp
uv run server.py

Inside a project you can drop the inline header — uv run uses the project's locked environment instead.

01Model-controlled

Your first tool

Why this is a tool

A tool is a function the model may call on its own initiative. Think of it as POST/RPC: it performs an action or a computation and may have side effects. The model reads your type hints and docstring — which FastMCP turns into a JSON Schema automatically — to decide whether and how to call it. So the docstring isn't a comment; it's the interface.

Add a tool that calculates a monthly mortgage payment. Notice how little ceremony there is: a decorator, type hints, and a clear docstring are the entire contract.

server.py · add below the sample data
@mcp.tool
def calculate_monthly_payment(
    principal: float,
    annual_rate_pct: float,
    term_years: int,
) -> dict:
    """Calculate the monthly payment for an annuity mortgage.

    Args:
        principal: Loan amount in euros.
        annual_rate_pct: Nominal annual interest rate, e.g. 3.65.
        term_years: Term of the loan in years.

    Returns:
        Monthly payment, total amount paid and total interest.
    """
    monthly_rate = annual_rate_pct / 100 / 12
    n = term_years * 12

    if monthly_rate == 0:
        monthly_payment = principal / n
    else:
        monthly_payment = principal * monthly_rate / (1 - (1 + monthly_rate) ** -n)

    total_paid = monthly_payment * n
    return {
        "monthly_payment": round(monthly_payment, 2),
        "total_paid": round(total_paid, 2),
        "total_interest": round(total_paid - principal, 2),
    }
✓
Checkpoint

Reload the Inspector. tools/list now returns one tool with a generated schema. Call it with a principal, rate and term and read the breakdown back.

▸What did FastMCP generate for me?

From the signature and docstring, FastMCP produced the tool's JSON Schema: parameter names, types (float, int), and the human-readable description the model sees. Vague names or a thin docstring produce a vague schema — and the model calls vague tools badly. Treat the signature as API design, because to the model, it is.

02Model-controlled

A second tool — and why you don't orchestrate

Why add a second one

A server has many tools, and the model chains them itself. You don't write the sequence — you describe each capability well and let the model decide the order. Add an affordability check and the model can compute a payment, then test it against income, without you wiring those two calls together.

server.py · add after the first tool
@mcp.tool
def affordability_check(
    monthly_payment: float,
    gross_monthly_income: float,
) -> dict:
    """Check whether a monthly payment fits a debt-to-income limit.

    Args:
        monthly_payment: Proposed monthly housing cost in euros.
        gross_monthly_income: Gross monthly income in euros.

    Returns:
        The debt-to-income ratio and whether it stays within the limit.
    """
    ratio = monthly_payment / gross_monthly_income
    return {
        "dti_ratio": round(ratio, 3),
        "max_allowed": MAX_DTI_RATIO,
        "within_limit": ratio <= MAX_DTI_RATIO,
    }
✓
Checkpoint

In a real client (not just the Inspector), ask: "Can someone earning €5,000/month afford €380,000 over 30 years at the annuity-30y rate?" Watch the model call both tools in sequence on its own.

▸Where a side-effecting tool would live

Both tools here are pure computations. A tool that changes something — logging an advice request to an internal system, say — would sit right alongside them. That side-effecting nature is exactly what separates a tool from a resource, and it's where audit logging and access control attach in production. Hold that thought for Step 05.

03App-controlled

Resources — read-only context

Why this is a resource, not a tool

A resource is read-only data addressed by a URI. It behaves like a GET: idempotent, no side effects. The application or user decides which resource to load as context — the model doesn't "invoke" it the way it invokes a tool. The rate table can't fail in a meaningful way and changes nothing, so it's context, not an action.

Expose the rate table two ways: a static resource for the whole table, and a resource template where the {product} segment is filled in at read time, so one function answers a whole family of URIs.

server.py · add after the tools
@mcp.resource("rates://current")
def current_rates() -> dict:
    """The full table of current mortgage rates (synthetic)."""
    return MORTGAGE_RATES


# Resource TEMPLATE — one function, many URIs:
#   rates://mortgage/annuity-20y-fixed
@mcp.resource("rates://mortgage/{product}")
def rate_for_product(product: str) -> dict:
    """Look up the rate for a single mortgage product."""
    rate = MORTGAGE_RATES.get(product)
    if rate is None:
        return {"product": product, "error": "unknown product",
                "available": list(MORTGAGE_RATES)}
    return {"product": product, "annual_rate_pct": rate}
✓
Checkpoint

The Inspector's Resources tab now lists rates://current and the rates://mortgage/{product} template. Read rates://mortgage/annuity-20y-fixed and you get a single rate back.

▸"I could have made this a tool" — why you shouldn't

You could. But a tool costs the model a decision and a round-trip, and signals that an action is available. A resource is cheap context the application can attach deterministically. Modelling read-only data as tools floods the model's tool list and blurs the line between "look something up" and "do something." Keep reads as resources and the model's choices stay clean.

04User-controlled

The prompt — where it all comes together

Why prompts exist at all

If you already have tools, why add a prompt? Because a prompt is a reusable workflow a person triggers deliberately — a slash-command in the client. It's the one primitive that ties the others together: this prompt tells the model to read the rate resource and call both tools, then produce structured advice. Same task, every time, started by a human — not improvised by the model.

server.py · add after the resources
@mcp.prompt
def mortgage_advice(
    client_name: str,
    loan_amount: float,
    term_years: int,
    gross_monthly_income: float,
    product: str,
) -> str:
    """Guided mortgage-advice workflow for an advisor."""
    return (
        f"You are a mortgage advisor preparing advice for {client_name}.\n\n"
        f"Follow these steps:\n"
        f"1. Read the resource `rates://mortgage/{product}` to get the rate.\n"
        f"2. Call `calculate_monthly_payment` with principal={loan_amount}, "
        f"the rate from step 1, and term_years={term_years}.\n"
        f"3. Call `affordability_check` with that payment and "
        f"gross_monthly_income={gross_monthly_income}.\n"
        f"4. Write a short, structured advice: product and rate, monthly "
        f"payment, total interest, and whether it is affordable. If it is "
        f"not within the limit, suggest one alternative.\n\n"
        f"Keep the tone factual. All figures are indicative."
    )
✓
Checkpoint

In your client, run the mortgage_advice prompt as a slash-command with a client's details. Watch the single trigger fan out into a resource read, two tool calls, and a written recommendation — every time, the same shape.

▸Prompt arguments are strings under the hood

The MCP spec passes prompt arguments as strings. FastMCP lets you annotate them with real types (float, int) for a better developer experience and coerces them for you. The return value can be a plain string, as here, or a list of structured messages when you need finer control over roles.

Reflect & ship

You now have a working server with all three primitives. The skill that outlasts this lab is the decision: given a new capability, which primitive is it? Run every idea through one question — who decides when it runs?

If the capability is……it's aControlled by
An action or computation the model should decide to runToolThe model
Data the model should read as context, where the app decides relevanceResourceThe application
A repeatable workflow a person deliberately startsPromptThe user

Where governance attaches

The control model isn't just pedagogy — it tells you where the controls go in a regulated deployment.

Tools — the side-effecting ones are where audit logging and RBAC belong. A tool can change the world, so every call is recorded.
Resources — read-only, so the concern shifts to data classification and PII handling: what context is allowed to reach the model.
Prompts — deliberately triggered, so they're the home of reproducible, reviewable behaviour: a workflow you can version and sign off.

From local to shared

You ran over stdio — the right choice for a local first server. For a server others connect to over the network, switch the transport:

server.py
if __name__ == "__main__":
    mcp.run(transport="http")  # Streamable HTTP for remote / shared use

That's also where an auth layer (OAuth) and a server registry enter the picture — the bridge from this lab to an enterprise deployment.

Where the protocol goes next

Two recent additions are worth knowing once the basics land. Tasks let a server run asynchronous, long-running operations instead of only call-and-respond. Sampling lets the server delegate inference back to the client — so the client owns the model and the keys, and the server needs no model credentials of its own. Both are deliberately out of scope for a first server; they're the next rung.
